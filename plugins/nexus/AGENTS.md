- The mod reaches Nexus only through the `nexus` CLI. `docs/cli.md` in the Nexus repository is the contract: the JSON each command prints, the exit codes (2 unreachable, 3 refused, 4 not found, 5 conflict, 64 invalid) and the watch stream. `hooks/model.ts` parses it at the boundary and keeps only the fields the mod reads. A field the contract requires and the mod reads (a `threads` row's `pylon`, `desired` and `attention`, `show`'s `desired`, `attention`, `attach` and `ports`, a thread's `seenAt` and `lastReplyAt`, each `Preview`'s `url`, a watch `state`'s `ports`) fails the parse when missing, so the pane says the CLI and the mod disagree instead of drawing a guess; a watch line that fails it ends the watch with that failure (`followWatch`). `ports: null` is the contract's "the node could not read them", not a missing field. Never hardcode or rebuild a URL, proxy or attach command: the CLI owns them, and a preview's link is its `url` as printed.
- Arguments: `--json` goes right after the verb (`nexus()` puts it there, after both words of `project add`, `session open` and `session close`, the CLI's two-word verbs), because `send` passes `--` before the message so a message starting with a dash is not read as a flag. `start` and `threads` pass `--flag=value`, since the CLI's `parseArgs` refuses a separate value that starts with a dash. `project add` passes its ID and URL after `--`, so one that starts with dashes is not read as an option, and `session open` and `session close` pass the thread and the pane or session ID after `--`, with `--title=` for a title that starts with a dash.
- Process budget: one poll at a time (`poller.isBusy`), only while the pane is open and shown, of `threads --all` for the list or `show` for the thread shown (none on the start form), and one `watch` for that thread (`watcher`). Both stop when the pane has closed (`closePane`, or the `ui.close` hook after `next`, since a hook beneath may keep it open), which `poll` also notices from `$.ui.panes()`. Publishing or unpublishing a port runs `preview --wait` or `unpreview` as a child of the poller (`changePort`), so the close kills that too and the change is forgotten; the port changes or is refused all the same. `pane.portChanges` keeps three things per port apart (`NexusPortChange`): what the last operation that succeeded left (`confirmed`, its preview or none, with its `seq`), the operation under way (`pending`) and the last failure. Starting or failing an operation leaves `confirmed` alone, so a port unpublished and then published again before a fresh `show` stays under Ports instead of the older snapshot's preview coming back. The details draw `confirmed` over what they list until a `show` asked for after it has come (`NexusShown.askedSeq`, `portChange`), since that `show` lists the port where it now belongs, or a later change by another client. The order is the module's `sequence`, taken when a confirmation is recorded and when a `show` is asked for, not the clock: a `show` asked for in the same millisecond as a confirmation would otherwise read as stale and keep a link another client had just closed. `show` can list a preview while `preview --wait` still waits, so a port with `pending` set is never offered for unpublishing: `holdingPort` refuses a second operation on a port, and nothing in the pane may offer one it would refuse. The changes are keyed by thread and then port, and leaving a thread keeps them, because its CLI runs on under the poller: a thread opened again still knows its operation under way. Only `startPane` clears them, since no older child runs then. Every publish and unpublish, from the pane, `/nexus unpublish` or the `preview` and `unpublish` tools, runs inside `holdingPort`, one module-level set of `thread:port` keys whose check and claim are one synchronous step, so no two operations on a port ever overlap: an unpublish that raced a publish could end first and the publish then expose the port again. A second operation is refused with the message pi-nexus uses too, not queued; the pane shows it as a notice, since what holds the port then is a command or a tool. `unpreview` must print a literal null (`parseUnpreviewed`): any other answer is a contract error, not a close. Only a linked port's preview (service `port-<n>`, `linkedPort`) can be unpublished, which `docs/cli.md` defines; `x` on any other row says why instead (an Effect of kind `say`). A CLI before 0.3.0 answers `unpreview` with `unknown command unpreview`, which `unpreviewPort` turns into the version it needs. A watch `state` event polls `show` at once, since the pylon or the parked tasks may have changed with it. `nodes` and `projects` are read on demand (`loadCatalog`), not polled. The ticker (`TICK_MS`) starts no process: it moves the `now` atom only while the shown run works, so the spinner and run clock tick. Tools start their own short-lived processes: `read` and `wait` each run a watch that ends with the call. The strip adds `pollStrip`: one `threads --all` (`$.process.run`) every `STRIP_MS` (10 s) from `session.start`, one at a time (`isStripBusy`), none while the strip is off or while the pane is shown on the list (the pane's poll writes the same `list` atom then). A strip answer that lands after the pane's newer read (`list.polledAt` at or past when the strip asked) or after the strip went off writes nothing. A port press carries the thread it was drawn for, and `changePort` drops one whose thread the pane has left.
- `followWatch` is the one reader of `nexus watch`, shared by the pane, `read` (until the first `state`) and `wait` (until `isSettled`, the timer or the call's abort). Calling `return()` on a `$.process.spawn` stream while a pull is pending kills the child at once (probed on 2.1.308 with `claude -p` and a pid file), so a stop never waits for the next line.
- Conversation rows come from each entry's raw pi-ai `model` messages, so a tool call and its result fold into one row with its arguments, output, line count and, for pi's edit tool, the result's `details.patch`, a real unified patch that `Code format="diff"` numbers as the file is. Without one (a write, or another tool's edit) `diffOf` builds hunks from the arguments, which carry no position, and the row says so; it keeps whole replacements up to `PATCH_CHARS` and the row counts the ones left out, since a row bounds each replacement but not their number. Rows keep each string argument, output and patch cut to a bound (`ARG_CHARS`, `OUTPUT_CHARS`, `PATCH_CHARS`), because `$.state` holds every row as JSON for each redraw. The engine draws a tree's first 100000 characters of text in the order written and cuts the rest, so an overdrawn conversation would cut the run line, the composer and the keys below it. The thread view therefore measures what it draws rather than estimating it: `drawnChars` counts the text the built tree carries (children, Code sources, Markdown texts, labels), the conversation gets what the rest of the view leaves of `DRAWN_LIMIT`, and it adds blocks newest first while they fit, a tools block by its newest steps, with a line saying how many earlier blocks and steps were left out. The newest block or step that alone is bigger than the room is cut (`cutTree`, which cuts Code and Markdown text and leaves out an element whose label would not be whole) with a note of what it lost; a fold's line goes with its newest step, a diff keeps whole hunks, and a Button, whose `label` is drawn whole or not at all, is left out rather than cut. A fold's line and a call's name are clipped to the width, one row each as Claude Code's are. `update` runs its function again when its write loses a race, so a flag set inside it is reset at the top. Elements are frozen plain data (`{ type, props, children }`, a Button's `press` handle beside them), so a cut copies them. An entry without `model` falls back to the CLI's `text`. The `read` tool gives the model the CLI's `text` instead, which keeps tool results.
- `isSettled(state, rows, sawWorking)` counts a thread done when it can no longer run (archived, deleted, parked, or its pylon failed: `pylon === 'failed'` or `failed` set), or when its run is idle with nothing queued and either the last row is not the person's message or this watch saw `run: working` before. The last covers a turn aborted before it wrote any text, which leaves the person's message last. pi-nexus mirrors this predicate with the same inputs, and the wait result's `needs_human` (`needsHuman` in hooks/tools.ts) with the same wording; change both together. `foldReply` builds `wait`'s reply from every assistant text after the last user message, a blank line apart, since a turn that calls tools writes one text per step. It folds each entry as the watch reads it, not the rows `applyEvent` keeps (`KEPT_ROWS`), so a turn longer than those still gives its first text, and it holds only the last `REPLY_CHARS` characters; `leftOut` renders it as `keepTail` would the whole text. An aborted or failed turn reports no reply rather than the one before it. A message just sent shows as queued, and one taken from the inbox but not yet answered is a trailing user row, so `wait` right after `send` does not return early. One watch poll prints its new entries before the state that changed with them, so `waitFor` settles at once only on a `state` event; an entry that looks settled counts after a quiet second (`QUIET_MS`), which covers a turn that started and ended between two polls with no state change printed.
- The pane's watch gathers events and writes them at most every `FLUSH_MS` (100 ms): the first after a quiet spell at once, after a zero wait that lets the lines of one read join it, the rest when the wait after the last write ends. A streaming answer prints a `live` event, the whole partial, about ten times a second, and the engine redraws a shown pane up to thirty, so without this each event would be a write and a redraw. `live` has an atom of its own (`NexusLiveShown`), since `$.state` copies a value whole and a live write would otherwise copy every row; each write sends the rows and state, from the watcher's own copy (it is their only writer, so nothing is read back), and the newest live event with no wait between the two, so no drawing reads one without the other: the CLI prints an answer's `entry` before the live event that drops its `partial`, and a drawing between them would show the answer twice. The answer streaming carries the key of the row it becomes (`row-<n>`, counted from the watch's first row through `dropped`, so trimming to `KEPT_ROWS` changes no key), so committing it swaps nothing. The conversation keeps its newest stops (blocks, fold lines, open steps) whose text fits `DRAWN_LIMIT`, estimates each one's rows (`rowsOf`, from the built tree), and draws only those the window reaches, at the bottom of a `flex-end` body with a negative `marginBottom`. The window is `pane.scroll`: null follows the end; else `anchor` is the block under the cursor and `rows` how far the bottom edge stands above that block's bottom, so blocks arriving below move nothing on screen. `j`/`k` move the cursor a block and the window only as far as shows its top (`moveTo` in `keys.ts`); `d`/`u` move the window half its height, through a block taller than it (`scrollTo`).
- Only the current pane watch writes `$.state` (`watcher === mine`): a stopped reader may still hold lines it read. `$.process.run` takes no abort signal, so the poll is a `$.process.spawn` child (`runChild`), and `stopPane` kills it through `poller.stop()`; `tests/pane.test.ts` holds that. A poll still checks `poller === current` before it writes, for lines read before the kill.

Session states (CLI 0.8.0): each session carries a `state` and the `id` `session close` takes, the pane except for a failed session in no pane (`failed-<hash>`); a control plane before it sends neither, which `parseSession` reads as running with the pane as its ID, and an unknown state is a contract error, since the Pylon tab offers a close by state. Rows, the cursor (`session-<id>`), closes under way and closes confirmed are keyed by ID. A paused session is never closed from the pane: `x` on it is a `say` with why (the CLI's 409 is the same refusal), and the ask-which dialog leaves it out. A close refused (409) or of a pane not open (404) shows the CLI's message as printed and is not run again. A failed close of a paneless session runs `nexus --version` and names 0.8.0 when the CLI is older. A wake can move a session's pane, so a close confirmed also hides a session with the closed one's `harnessSessionId`, and an open confirmed (`OpenedSession` carries no harness session ID) is settled by its pane (unless the session there has a harness session ID listed before, as stale details show the pane's earlier one), else by a session of its harness and title whose harness session ID the details did not list when it was confirmed (`before`, since a session that existed and moved keeps its own), one session per open (`listedOpens`); a session with no harness session ID matches only by pane, and an open nothing matches keeps its row until `SESSION_SETTLE_MS`. Attach: 2.1.310 gives a mod no terminal to hand over (`$.process.run` and `spawn` pipe stdio, with no pty, inherit or suspend, and `$.ui` runs no external program), but Herdr can: inside Herdr (`HERDR_ENV=1` and `HERDR_WORKSPACE_ID`, read once at session start into `herdrWorkspace`, and drawn as `scene.inHerdr`), Enter, Attach in the menu and `/nexus session attach` make a tab in that workspace with `herdr tab create … --focus` and type `<cli> attach <id>` into its shell with `herdr pane run`, so the detach leaves the tab at its shell. That line goes through a shell, so the ID must match `FULL_ID` and both words go through `shellQuote` in `attachCommand`, which every attach command shown or copied comes from, so each names the CLI the `cli` option names (plain `nexus` by default). `/nexus session` splits its arguments as a shell does (`words`): quotes anywhere in a word, so `--title="two words"` is one title. Outside Herdr, or when herdr fails, they give `nexus attach <thread>` to run in a terminal or a Herdr tab, with the attach hint pi-nexus shows too (`ATTACH_HINT`) and herdr's failure first; `y` always copies. No model tool opens, closes or attaches, and a CLI before 0.5.0 answers `unknown command session`, which `newer` turns into the version it needs. The mod never runs `attach` itself, so an attach's failure, such as a CLI before 0.9.0 trying ssh, which upgraded nodes refuse, shows only in the tab or terminal that runs it.
- Changes (CLI 0.6.0): every `changes` or `diff` read reaches into the pylon, counts as human activity and wakes a paused one, so reads follow one rule and never a timer. `readChanges` runs only while `show` says the pylon runs and the thread is active or idle, or the person asked to wake it (Enter or `r`, `NexusCheckout.isWanted`): when the tab is first shown (`firstRead`, or any details while the tab still waits for a first read, so a read the pane's close cut short runs again), and when new details (`noticeCheckout`, from `poll` with the details before) end a turn, or start the pylon while a wake or the first read waits (`checkoutTrigger`). One `changes` child and one `diff` child at a time (`changesChild`, `diffChild`), each stopped with the poller (`Promise.race` with `poller.stopped`) and when the pane leaves the thread (`leaveCheckout`). The check and claim of `changesChild` are one synchronous step, so two asks at once start one child; a second ask while a read runs is that read; `c` during a read leaves it running and its reply, for the old base, is dropped and read again for the new one. A diff opened on a pylon not running reads nothing and offers the wake instead; a finished changes read re-reads the open diff even while the details still say paused (`readDiff`'s `isAwake`), since the CLI answers only once the pylon runs. The tree draws only the rows on screen (each is one row by construction, `treeStop` keeping the rest navigable), since 3000 files drawn whole pass the 100,000 characters the engine draws of one tree. The diff is kept in `$.state` (`diff` atom) parsed into at most `DIFF_ROWS` rows of at most 400 characters each, and drawn windowed to the rows shown. `c` steps through `BASES` (start, turn, head: no flag, `--turn`, `--uncommitted`) and is kept in `$.store` under `changesBase`; `loadChangesBase` turns the boolean `uncommitted` an earlier version kept into its base and deletes that key. A CLI before 0.6.0 answers `unknown command changes`, which `newer` turns into the version it needs, and one before 0.11.0 refuses `--turn` as an unknown option, which `checkoutFailure` names from `nexus --version`; a refused base (`isNoBase`: no `refs/nexus/base`, or no latest-turn snapshot) suggests the next base. The turn snapshot exists only for harness replies: a Claude worker's or an interactive session's work has none, so its refusal shows as printed. Esc in normal mode hands the keys to the prompt (no event reaches the pane), so only `h` leaves a diff.
- Claude Code worker threads (CLI 0.17.0): `show`'s `claudeWorker` marks one (`NexusDetail.conversation` is `claude`, `worker` its launch); the thread has no `conversationId`, so the old `hasConversation` would have hidden its conversation and composer. `threads` rows carry no `claudeWorker`, and a worker's turn is the row's `sessionTurnRunning`, which `parseThread` folds into `agentTurnRunning`. `nexus watch` streams no Claude transcript (only state), so `poll` follows a worker's `show` with one `nexus conversation` (`readClaude`) into the `claude` atom, and the render puts its rows, run and queue in the watch's place (`claudeWatch`), the rest of the view unchanged. `parseClaudeConversation` folds the `ClaudeEntry`s into `NexusRow`s: Claude Code's tools are renamed to pi's (`CLAUDE_TOOLS`: Edit's `old_string`/`new_string` become an `edits` entry, so `diffOf` draws it), a `result` settles its call by `toolUseId` (`settle`, shared with pi's), queue operations move only the queue, as the CLI's `queuedOf` does, and an entry kind the mod does not know is skipped, as docs/cli.md asks. Each row carries its entry's position in the whole transcript (`NexusRow.entry`, the CLI's `dropped` plus its index), and `blocks` keys it `entry-<n>`, so a 3,000-entry window that slides past an entry no row shows moves no key, cursor or scroll anchor. `send` runs with `SEND_MS` (160 s), above the 120 s the CLI retries a worker's paused pylon. While the Herdr tab the pane opened for an attach still runs it (`isAttached`: `herdr pane process-info` shows a foreground group other than the shell's, `isPaneRunning`), `poll` reads no transcript; a detach or a closed tab clears it. `send` answers `{ claude: { outcome, resumed } }` for a worker (`parseSent`, `sentText`). The `read` and `wait` tools read `show` first and, for a worker, its transcript (`claudeThread`); `waitForClaude` reads both every `CLAUDE_WAIT_MS` and judges them with `isWorkerIdle` (`claudeState`), which, unlike the harness's `isSettled`, counts a transcript ending at an unanswered prompt as done (reply null): an idle reading settles only when the one a full `CLAUDE_WAIT_MS` before was idle too, unless it saw the turn run, since a message just typed reaches the transcript and the turn's report a moment later. A deadline never shortens that wait: one too near for the next reading returns `timed_out`, unsettled. A reading that fails unreachable or failed does not end the wait: it reports `outage` and reads again, as the harness's watch outlives an outage. The harness's abort and retry are not offered for a worker, and the latest-turn snapshot does not exist for it.
- Delete asks through `$.ui.ask` with Keep first, the dialog's default, naming the thread's title (from a fresh list when the pane has none); a dismissed or headless ask keeps the thread.
- `claude plugin validate` passes a `.catch` handler bound inside `register`, but the module then fails to load: a handler must be a function declared at the top of the hooks module (`failedTool`).
- Under Claude Code's Bash sandbox, `claude -p --plugin-dir plugins/nexus "/nexus …"` runs the commands with no model call, which makes a quick check against a fake CLI (`--settings '{"pluginConfigs":{"nexus":{"options":{"cli":"/path/to/fake"}}}}'`). There `$.tool.register` throws `Failed to start server` because the sandbox forbids binding a port, so `session.start` is skipped; outside the sandbox it registers. The sandbox also blocks the SOCKS proxy, so the real control plane is reached only from an unsandboxed session.
- `claude plugin test` prints no `console.log` output. A probe test can fake the CLI with the test's own `on('process.run', …)` answering `{ value: { exitCode, stdout, stderr, … } }` and an `on('process.spawn', async function* …)` that yields chunks and returns `{ value: { code, signal } }`.
- The engine gives a Button with children a `label` holding their text, so `inlineText` counts the label only for a Button without children; counting both made every full-width Button measure two rows and the Changes tree scroll past its rows.
- A Button ignores `wrap="truncate-end"` on a child Text (probed live on 2.1.310); a Text around the Button is refused as "Button inside an inline element". Pylon's session rows therefore use `clip` to find the prefix that fits in terminal cells, then `cutTree` to keep that prefix's characters and styling, plus an ellipsis. `rowsOf` measures the same clipped row; the failure reason and cursor hint stay outside it and wrap.
