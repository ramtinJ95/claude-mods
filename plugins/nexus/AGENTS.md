- The mod reaches Nexus only through the `nexus` CLI. `docs/cli.md` in the Nexus repository is the contract: the JSON each command prints, the exit codes (2 unreachable, 3 refused, 4 not found, 5 conflict, 64 invalid) and the watch stream. `hooks/model.ts` parses it at the boundary and keeps only the fields the mod reads. A field the contract requires and the mod reads (a `threads` row's `pylon` and `desired`, `show`'s `desired`, `attach` and `ports`, each `Preview`'s `url`, a watch `state`'s `ports`) fails the parse when missing, so the pane says the CLI and the mod disagree instead of drawing a guess; a watch line that fails it ends the watch with that failure (`followWatch`). `ports: null` is the contract's "the node could not read them", not a missing field. Never hardcode or rebuild a URL, proxy or attach command: the CLI owns them, and a preview's link is its `url` as printed.
- Arguments: `--json` goes right after the verb (`nexus()` puts it there), because `send` passes `--` before the message so a message starting with a dash is not read as a flag. `start` and `threads` pass `--flag=value`, since the CLI's `parseArgs` refuses a separate value that starts with a dash.
- Process budget: one poll at a time (`poller.isBusy`), only while the pane is open and shown, of `threads --all` for the list or `show` for the thread shown (none on the start form), and one `watch` for that thread (`watcher`). Both stop on the pane's close, which `poll` also notices from `$.ui.panes()`. Opening a port runs `preview --wait` as a child of the poller (`openPort`), so the close kills that too and the opening is forgotten; the port is published or refused all the same. A watch `state` event polls `show` at once, since the pylon or the parked tasks may have changed with it. `nodes` and `projects` are read on demand (`loadCatalog`), not polled. The ticker (`TICK_MS`) starts no process: it moves the `now` atom only while the shown run works, so the spinner and run clock tick. Tools start their own short-lived processes: `read` and `wait` each run a watch that ends with the call.
- `followWatch` is the one reader of `nexus watch`, shared by the pane, `read` (until the first `state`) and `wait` (until `isSettled`, the timer or the call's abort). Calling `return()` on a `$.process.spawn` stream while a pull is pending kills the child at once (probed on 2.1.308 with `claude -p` and a pid file), so a stop never waits for the next line.
- Conversation rows come from each entry's raw pi-ai `model` messages, so a tool call and its result fold into one row with its arguments, output, line count and, for pi's edit tool, the result's `details.patch`, a real unified patch that `Code format="diff"` numbers as the file is. Without one (a write, or another tool's edit) `diffOf` builds hunks from the arguments, which carry no position, and the row says so; it keeps whole replacements up to `PATCH_CHARS` and the row counts the ones left out, since a row bounds each replacement but not their number. Rows keep each string argument, output and patch cut to a bound (`ARG_CHARS`, `OUTPUT_CHARS`, `PATCH_CHARS`), because `$.state` holds every row as JSON for each redraw. The engine draws a tree's first 100000 characters of text in the order written and cuts the rest, so an overdrawn conversation would cut the run line, the composer and the keys below it. The thread view therefore measures what it draws rather than estimating it: `drawnChars` counts the text the built tree carries (children, Code sources, Markdown texts, labels), the conversation gets what the rest of the view leaves of `DRAWN_LIMIT`, and it adds blocks newest first while they fit, a tools block by its newest steps, with a line saying how many earlier blocks and steps were left out. The newest block or step that alone is bigger than the room is cut (`cutTree`, which cuts Code and Markdown text and leaves out an element whose label would not be whole) with a note of what it lost; a fold's line goes with its newest step, a diff keeps whole hunks, and a Button, whose `label` is drawn whole or not at all, is left out rather than cut. A fold's line and a call's name are clipped to the width, one row each as Claude Code's are. `update` runs its function again when its write loses a race, so a flag set inside it is reset at the top. Elements are frozen plain data (`{ type, props, children }`, a Button's `press` handle beside them), so a cut copies them. An entry without `model` falls back to the CLI's `text`. The `read` tool gives the model the CLI's `text` instead, which keeps tool results.
- `isSettled(state, rows, sawWorking)` counts a thread done when it can no longer run (archived, deleted, parked, or its pylon failed: `pylon === 'failed'` or `failed` set), or when its run is idle with nothing queued and either the last row is not the person's message or this watch saw `run: working` before. The last covers a turn aborted before it wrote any text, which leaves the person's message last. pi-nexus mirrors this predicate with the same inputs, and the wait result's `needs_human` (`needsHuman` in hooks/tools.ts) with the same wording; change both together. `foldReply` builds `wait`'s reply from every assistant text after the last user message, a blank line apart, since a turn that calls tools writes one text per step. It folds each entry as the watch reads it, not the rows `applyEvent` keeps (`KEPT_ROWS`), so a turn longer than those still gives its first text, and it holds only the last `REPLY_CHARS` characters; `leftOut` renders it as `keepTail` would the whole text. An aborted or failed turn reports no reply rather than the one before it. A message just sent shows as queued, and one taken from the inbox but not yet answered is a trailing user row, so `wait` right after `send` does not return early. One watch poll prints its new entries before the state that changed with them, so `waitFor` settles at once only on a `state` event; an entry that looks settled counts after a quiet second (`QUIET_MS`), which covers a turn that started and ended between two polls with no state change printed.
- The pane's watch gathers events and writes them at most every `FLUSH_MS` (100 ms): the first after a quiet spell at once, after a zero wait that lets the lines of one read join it, the rest when the wait after the last write ends. A streaming answer prints a `live` event, the whole partial, about ten times a second, and the engine redraws a shown pane up to thirty, so without this each event would be a write and a redraw. `live` has an atom of its own (`NexusLiveShown`), since `$.state` copies a value whole and a live write would otherwise copy every row; each write sends the rows and state, from the watcher's own copy (it is their only writer, so nothing is read back), and the newest live event with no wait between the two, so no drawing reads one without the other: the CLI prints an answer's `entry` before the live event that drops its `partial`, and a drawing between them would show the answer twice. The answer streaming carries the key of the row it becomes (`row-<n>`, counted from the watch's first row through `dropped`, so trimming to `KEPT_ROWS` changes no key), so committing it swaps nothing. The conversation's room and what the run changes (the live blocks, and the tool blocks from the oldest call still running) are measured in steps of `ROOM_STEP`, so the older blocks drawn above do not change as an answer grows or the run clock ticks, and a reader scrolled up is not moved.
- Only the current pane watch writes `$.state` (`watcher === mine`): a stopped reader may still hold lines it read. `$.process.run` takes no abort signal, so the poll is a `$.process.spawn` child (`runChild`), and `stopPane` kills it through `poller.stop()`; `tests/pane.test.ts` holds that. A poll still checks `poller === current` before it writes, for lines read before the kill.
- The pane follows Claude Code's own transcript and paints only with theme keys; `tests/console.test.ts` fails on any other colour. As a capture of the real transcript shows it under `dark-ansi`: the prompt row is `❯ ` in `subtle` and its text in `text`, continuation lines under the text; an answer's `⏺` is `text` and its prose Markdown's own default; the spinner and its verb are `claude`, its facts `subtle`; key hints are `dimColor` Buttons, the engine painting the hotkey letter. A collapsed diff is `wrap="truncate-end"`, an opened one wraps. The dock's background is the engine's, not the mod's: every cell it writes there carries the theme's `composerSidebarBackground` (`color8`, SGR 100, under `dark-ansi`), and no element prop clears it; a custom theme (`~/.claude/themes/<name>.json` with `base` and `overrides`) can. freeze 0.2.2 keeps a bright foreground after SGR 39 and a background after SGR 49, so a capture for it needs each 39 rewritten as 37 then 39 and each 49 as an explicit background first, and `capture-pane -N` keeps the trailing cells that carry the dock's background. Markdown and Code wrap themselves and the engine scrolls the body (`scroll` follows the end), so the views size nothing to the pane's height. Clipping a list row's title counts terminal cells (`cells` in `model.ts`): East Asian wide characters and emoji take two.
- Buttons with hotkeys are left out only while a drawn field has the keys (`pane.field` and the view drawing that field): a letter typed into the composer or the filter must not press one, and a composer the thread's change hid (an archive, a failed pylon) gives them back. A key pressed then sets the field to none, so the composer does not come back focused. `m` and `f` draw the field with `autoFocus`; an empty Enter hands the keys back. `$.ui.focus` from the mod is asked too, and its refusal is ignored: the field is drawn either way, and the test kit answers no plugin's `ui.focus` ("no implementation"). Hotkeys are one lowercase letter or digit, Shift adding nothing, so `d` deletes and `p` retries a pylon.
- Folds, tool rows and closed groups default open or closed in the view (a fold opens while a step runs or failed, a closed group while a filter matches it); `pane.toggled` records only what the person changed, keyed `fold-<first call id>`, `tool-<call id>`, `closed-<project>`, and is cleared when another thread opens. Each change of the filter clears the `closed-` keys, so the filter opens what it matches afresh, as the dashboard's does.
- A visit is recorded (`nexus wake`) once per opened thread, from its first `show`, and only for an active or idle thread, as the dashboard records a page visit. The start form's Enter submits with the field's own text (`startSubmit(change)`), since Enter can come before that field's change event. A start that ends after the person left the form, or opened another, only says how it went: the form carries the number of the submission it waits on (`request`), and the start's end checks it and switches the view in one `update` of the pane, so no await falls between them; one that ends after the pane closed sets the view, and `showThread` starts no watch without a `poller`, so the watch starts when the pane opens again.
- There is no `session.end` hook: `/clear` raises `session.end` with no `session.start` after it, and stopping there would leave an open pane with no processes. A reload kills the children with the module and runs `session.start` again, which restarts them when `$.ui.panes()` still lists the pane.
- `/nexus` is registered `immediate`, so it runs during a turn. On 2.1.309 the pane it opened with `focus` did not get the keys (live test): `openPane` asks once more after `REFOCUS_MS` when `$.ui.panes()` says it is still open and not focused (`stopPane` also cancels that timer, so a closed pane is not reopened), and both views draw the focus chord while `isFocused` is false. Whether the second ask takes is not yet observed.
- Delete asks through `$.ui.ask` with Keep first, the dialog's default, naming the thread's title (from a fresh list when the pane has none); a dismissed or headless ask keeps the thread.
- `claude plugin validate` passes a `.catch` handler bound inside `register`, but the module then fails to load: a handler must be a function declared at the top of the hooks module (`failedTool`).
- Under Claude Code's Bash sandbox, `claude -p --plugin-dir plugins/nexus "/nexus …"` runs the commands with no model call, which makes a quick check against a fake CLI (`--settings '{"pluginConfigs":{"nexus":{"options":{"cli":"/path/to/fake"}}}}'`). There `$.tool.register` throws `Failed to start server` because the sandbox forbids binding a port, so `session.start` is skipped; outside the sandbox it registers. The sandbox also blocks the SOCKS proxy, so the real control plane is reached only from an unsandboxed session.
- `claude plugin test` prints no `console.log` output. A probe test can fake the CLI with the test's own `on('process.run', …)` answering `{ value: { exitCode, stdout, stderr, … } }` and an `on('process.spawn', async function* …)` that yields chunks and returns `{ value: { code, signal } }`.
