- The hooks module has no Node. Core sockets, transcripts and processes go through `bridge/`: `cli.mjs` runs one operation per `$.process.run`; `watch.mjs` is one machine's watcher started with `$.process.spawn`. A spawned child gets its stdin as one string and then EOF, so a watcher cannot take commands: the fleet restarts a machine's watcher when its watched set changes, leaving other machines' running.
- Herdr Core (`hc`, 0.1.18+) is the only backend; the older Herdr TUI socket and SSH bridge are gone, as upstream pi-shepherdr dropped them (howaboua-pi-stuff `9f5ae2e`, `dev`). Core is JSON-RPC 2.0 NDJSON, one request per connection (`core.mjs`): `HC_TERMINAL_SOCKET` inside a Core terminal, else `hc connect` over stdio, which starts a Core when none runs and picks it by `HC_SESSION`. The API's docs ship inside the `herdr-core` binary (schemars text); `hc schema` prints them as JSON Schema but needs a running Core. Errors carry `data.kind` (`not_found`, `blocked`, ...).
- Core addresses (`t7`; `machine/t7` for a connected machine's terminal through this Core) never move or get reused, so `paneId` and `terminalId` are both the address on the worker's own machine. Labels outlive a kept terminal's program: a worker counts only while its program reports status (`status.app` `pi` with label `pi.session_file`, or `claude-code` with `claude.session_id`). Pi clears both between sessions (/new, /resume), so a live terminal without them settles as working, not closed.
- `cli.mjs` splits controller operations, which run beside Claude Code and own the sender identity, profiles, preparation and launches, from `machine.*` operations, which touch only the Core and files of the machine they run on. A remote machine runs the same `cli.mjs`/`watch.mjs` through `hc exec --on <id> -i` (stdout and exit code pass through, so no exec result fields are parsed), from a copy installed once per bridge version (content hash); there the bridge reaches its own Core with `hc connect`, `HC_SESSION` passed by `--env`. Anything needing this terminal, such as `HC_TERMINAL_ID`, stays in a controller operation. Controller operations resolve a machine once and pass its catalog entry down; `onMachine` tags remote records with its ID and name.
- Spawn runs `terminal.run` from the controller's own Core (`on` for another machine, `caller` this terminal), so the worker is this terminal's child and the Herdr window nests it; `outlive_parent` keeps it when Claude Code exits, as Herdr tabs did, and `no_notify` keeps Core's notes out of this session. argv[0] is resolved to an absolute path on the worker's machine (`machine.target`), since Core reads a bare name matching a template as that template. Herdr placement is labels: `herdr.space` and `herdr.tab` IDs (a tab joins a space some live terminal on that Core advertises); without them the worker is a background terminal. A failed start reads the screen for its reason, then the controller kills and removes the terminal.
- Remote machines are Core's catalog (`machine.list`: `id`, `name`, `host`, `state`, `session`), addressed by stable ID or exact current name; requests omit `machine` (or say `local`, stripped at parsing) for this one. Only `connected` machines are used; others are reported unavailable. Remote code must run on the Node a machine has, so avoid recent built-ins there (`Map.groupBy` and the like).
- Time limits flow down from the hooks' `call` timeout as `budgetMs`: nested remote calls and blocking waits derive theirs from it, and a remote machine gets the time left, not a deadline, since its clock may differ. `$.process.run` allows ten minutes at most (`LONGEST_CALL_MS`), as does `hc exec` (`--timeout` 600 s).
- `$` reaches only top-level functions of `register.ts`; imported modules get closures. `tool.call` uses `bridgeOf($)` with its own `$`, because a hook's 10 s budget only pauses while that hook's own `$` calls are in flight.
- `session.start` does not repeat on `/clear`, `/resume` or `/branch`. Bind the fleet and its saved file to the current session at turn, tool and command entry, and retire it on `session.end`. Do not rely on classic hooks, which managed policy can bypass.
- A blocking call or an answer being entered leases its worker; the watcher skips leased workers and reconciles them when the last lease ends. Settlement compares the worker's latest input ID with `seenInputId`, so a reply is reported once whichever path sees it.
- `spawn` and `assign` return after delivery unless `blocking: true` (a profile's `blocking` overrides spawn), as upstream since 0.2.26. A record's `task` is the task whose outcome is still owed, cleared when its done report is produced; `scope` and `latest` are the agent's first task and its latest differing one, which the compaction briefing gives as `instructions`.
- Workers a session spawned are its `children` in saved state: machine, terminal address, name, earlier addresses (`aliases`) and an opaque `launch` (`kind`, `session`, `cwd`, profile args) only the bridge reads. A profile whose own arguments open an existing session gets none. `send` and `assign` pass a matching child to the bridge's `deliver`, which asks the worker's machine where it is (`machine.revive`): its own terminal if live, else one hosting its session, else a live terminal answering to the target (then not the child), else a relaunch with the adapter's `resumeArgs`, whose session is verified before delivery. Pi restores model, thinking and name from the session, so those flags are stripped; Claude Code restores only the conversation, so its arguments are passed again with `--session-id` swapped for `--resume`, which keeps the ID. Only a `resumed` delivery moves a child to its new address. A name belongs to the newest child that had it; `/quit` never relaunches.
- A close the controller asked for (`/quit`, `/shepherdr close-idle`) is marked in `Fleet.closing` before the bridge call, since the watcher's `closed` event can arrive before the call returns; a marked `closed` settles without a report, except in a blocking call (`force`), which would otherwise wait forever. The bridge says `closed: true` only when it removed the terminal, and the hooks then drop the watch. `close-idle` skips children with a lease, an owed `task` or `working` status, so a result not yet reported is never closed over. Pi decides idleness in its receiver (a `close-idle` frame whose text is `/quit` and sender `<herdr_sender kind="idle-close" />`); Claude Code has no such moment, so its status and open question are checked just before `/exit`.
- Claude Code with a background shell still running can take longer than `EXIT_TIMEOUT_MS` to leave after `/exit`: `/quit` then fails with "still running" while the terminal finishes moments later and stays in Core as `finished`.
- Records are keyed by machine and terminal address. Every watcher runs beside Claude Code and follows this Core's `events.subscribe`, which covers connected machines' terminals (`<name or id>/t7`; both are normalized to the ID, and a name the watcher does not know rereads `machine.list`, since a rename changes it in later events). Events carry no reliable status, so the watcher reads `terminal.get` per event and emits only changes of status or session label, `closed` once a terminal finished or went; a `missed` snapshot rechecks every target. A session label can land after the status it settles with, and the fleet's check then moves the watch to the new transcript. Core heartbeats a subscription every 15 s; `subscribe` treats 45 s of silence as broken, 10 s before the first snapshot. Transcript watchers start before taking sizes, so a write between the two is not lost.
- Reports raised during a main turn wait in the fleet's outbox and are appended after the next main-loop tool call; what the turn never reached is submitted as the next prompt when it ends. Register the drain wrapper before tool handlers that return without `next`, including `agents`, or their calls bypass it. `$.prompt.submit` resolves only when its turn starts: never await it from `turn.complete`. Subagent runs raise `turn.complete` with `agentId` but no `turn.start`.
- After automatic compaction, which resumes mid-turn without `turn.start`, the briefing joins the compacted messages. Between turns (`/compact`, a notes-compaction window) another plugin may replace the conversation after this hook, so it is only marked due and appended at the next turn start. The orchestration guidance rides along when the user chose a mode.
- Current Pi Ask publishes each open question as a `shepherdr-extension-message` entry (text and reply template, no prompts) and takes its answer as an `extension-reply` peer frame, which reaches a blocked worker without a turn; that is the only route to an Ask run inside a Code Mode `exec` cell, whose call never appears as an `ask` tool call. The report carries Ask's own text and reply template as `question`, not prompts. Only Ask's messages are read: `answer` sends Ask's JSON answers, and other extensions' messages have no answer shape in the tool yet. The terminal-driving answer for older Ask is gone, as upstream dropped it; the reader still reports older `pi-ask-active` questions, which the user answers in the worker's terminal.
- Background Pi Asks (`delivery: "steer"`) are found by the transcript watcher, which reads only what each write appended and parses the transcript only when that holds an Ask entry; it scans once at start for Asks opened earlier. They settle through the same `question` path as blocking Asks. On a remote machine `hc exec` returns output only at exit, so the transcript watcher runs there in `once` mode: each run ends at the first write (or after 540 s) with a `sizes` line, which the relay passes to the next run so writes between runs are not missed.
- `bridge/vendor/*.mjs` and `profiles/` started as copies of pi-shepherdr (howaboua-pi-stuff `1f189a2`) and are owned here; nothing goes back upstream. Keep the peer frame compatible with the receiver pi-shepherdr workers run (`PEER_PROTOCOL`, the `message`, `commands`, `close-idle` and `extension-reply` kinds). Its receiver publishes `<session file>.shepherdr-<first 16 hex of sha256(HC_TERMINAL_ID)>.json`; identity checks go through Core (`terminalPeer`).
- Since pi-shepherdr 0.2.20 (upstream `e792257`, `5ebc24d`) a Pi worker publishes its receiver from `resources_discover`, after Core already reports it idle with a session. A missing receiver file is a delivery error, with no terminal fallback, as in upstream since 1.0.0 (`resolveReceiver`), so spawn and resume await the adapter's `awaitStartup` (up to 30 s for the inbox file) before delivering and fail past it; attached workers are not waited for.
- Spawn launches Pi with `--shepherdr-worker` (pi-shepherdr 0.2.23+). pi-shepherdr 1.0.0 still registers `--shepherdr-profile-prompt` but never reads it, so a Pi profile's prompt goes in the first task's `context` as `<initial_worker_profile>` ahead of the delegation guidance, the shape upstream's own controller sends (`messages/attribution.ts`); the receiver shows `context` after the sender line. Pi 1.4 exits on a flag no extension registered (`Unknown option: --shepherdr-…`), so spawned Pi workers require pi-shepherdr 0.2.25 (the first with Core support) and the adapter's `startupFailure` names it from the screen.
- Writing to a child's stdin after it exited (`hc exec` or `hc connect` refused) raises `EPIPE` on the pipe, which kills the bridge process when nothing listens. Both paths ignore stdin errors and let `close` report the cause from the exit code and stderr.
- `answer` returns once the worker took the answers and never waits for the work it resumes, which its watch reports. For a blocking Ask it still waits until Core stops reporting the worker blocked on it (bounded at 15 s; past that the worker is reported as it stands): the check that follows the answer's lease would otherwise report the same question again.
- New worker kinds are adapters in `bridge/workers/` exposing `kind`, `program`, `executable`, `launchArgs`, `resumeArgs`, optional `launchLabels` and `localOnly`, `sessionPath`, `savedSession`, `isReady`, `view`, `deliver`, `commands`, `closeIfIdle`, `answer` and `answerStatus`, with questions and answers in the shared shape documented in `workers/index.mjs`; shared code asks the adapter (`workerFor`, `workerOfKind`) rather than testing kinds, and adapters share `envelope.mjs` (the delivered text), `answers.mjs` (answer checks) and the vendor reader's `scanBackward`/`cachedView`. The hooks side knows no kind; it only completes a `session` route (`sendRoute`), the one thing the Node bridge cannot do.
- Claude Code workers take tasks and answers through `$.session.send`, which reaches sessions on this machine only, so `onMachine` rejects any remote result carrying a `session` route and `spawn` refuses Claude profiles on another machine. Core's `terminal.send` is used only for slash commands: `/quit` types `/exit`, waits for Claude Code to stop reporting, then kills and removes the terminal (an attached session's terminal would otherwise keep its shell).
- Claude Code holds a peer message for its person when exactly one side bypasses permissions (`bypassPermissions`, or plan where bypass is available); the worker would idle while its controller waits, and `$.session.send` reports nothing. Spawn therefore passes `--settings` with `crossSessionInbound: "accept"`. Only the last `--settings` flag applies, so `profileArgs` folds a profile's own into that one. Attached, non-spawned sessions keep their own setting.
- A Claude worker's open `AskUserQuestion` is answered by its own Shepherdr (`hooks/worker.ts`): the `tool.call` hook races the dialog's `next(e)` against an answer frame keyed by the call's `tool_use_id`. Returning first closes the dialog; the abandoned `next` settles as a rejection the model never reads. `session.receive` consumes every message that is wholly a frame, open or not, so none reaches the model; the controller escapes `<` in the frame's JSON so answer text cannot close it early. `origin.plugin` is only the sender's claim: never guard on it. A worker without this mod loaded cannot be answered this way; `answered` then fails after 10 s.
- Claude Code writes an `AskUserQuestion` call to its transcript only once it settles, so the worker's hook publishes the open question to `$XDG_DATA_HOME/claude-shepherdr/asks/<session id>.json` before calling `next(e)` and writes `{}` after; the bridge reads it uncached beside the transcript, whose recorded result outranks a stale file. A worker without this mod reports a plain `blocked`.
- Claude Code reports its own status to Core (OSC 7501, `app=claude-code`, `kind` permission or question when blocked); Core reads nothing from the screen. `view` still reads the published question whatever Core's status. Its session ID reaches Core as the terminal label `claude.session_id`: spawn sets it from the profile's `--session-id`, and the worker's own Shepherdr (`publishSession`) relabels at session start and each turn start, since `/clear` and `/resume` change it without a `session.start`. Until that worker's next turn its label names the previous session.
- Claude transcripts (`$CLAUDE_CONFIG_DIR/projects/<cwd, non-alphanumerics as dashes>/<session id>.jsonl`) chain by `uuid`/`parentUuid`; a compaction boundary has no `parentUuid` and continues through `logicalParentUuid`. Inputs are human `user` rows, peer messages (`user`, `isMeta`, `origin.kind: "peer"`), and mid-turn arrivals recorded as `attachment` rows of type `queued_command`; tool results, compact summaries, local command rows and interruptions are not. Spawn passes `--session-id`, so the session is known before its transcript exists; until then `sessionPath` is undefined and settlement runs on Core status alone.
- Claude Code trusts exact folders, not their children. A spawn stuck at Pi's or Claude Code's trust prompt reads the screen and says so before rolling back; trusting a folder is the user's decision.
- Claude profiles come from `$XDG_CONFIG_HOME/claude-shepherdr/profiles` when it exists, else `claude-profiles/`; Pi Shepherdr's directory never holds them, since its loader rejects their fields. A name in both sets is refused. `--plugin-dir` shadows an installed copy of the same plugin, which is how a live test gives workers a development build (a temporary Claude profile whose `claude_args` pass it).
- `fs.watch` fails with `EMFILE` and localhost TCP is blocked inside Claude Code's Bash sandbox, so `watch.mjs`, `wait`, `answer` and peer delivery cannot be probed from there; the mod's own processes are not sandboxed. The sandbox also refuses Core's socket unless `allowUnixSockets` lists it (`~/.local/state/herdr-core/<session>/<session>.sock` on macOS), and cannot start a scratch Core.
- Claude Code draws `$.ui.status` text as `<plugin name>: <text>`. Pass the text alone; a `shepherdr:` prefix of its own shows the name twice.
