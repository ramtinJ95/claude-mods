- The hooks module has no Node. Herdr sockets, transcripts and processes go through `bridge/`: `cli.mjs` runs one operation per `$.process.run`; `watch.mjs` is one machine's watcher started with `$.process.spawn`. A spawned child gets its stdin as one string and then EOF, so a watcher cannot take commands: the fleet restarts a machine's watcher when its watched set changes, leaving other machines' running.
- `cli.mjs` splits controller operations, which run beside Claude Code and own the sender identity, profiles and preparation, from `machine.*` operations, which touch only the Herdr they run on. A remote machine runs the same `cli.mjs`/`watch.mjs` over SSH with `--session`, from a copy installed once per bridge version (content hash); anything needing this pane, such as `HERDR_PANE_ID`, must stay in a controller operation. Controller operations resolve a machine once and pass its catalog entry down; `onMachine` tags remote records with their machine.
- Remote machines are Herdr's catalog (`herdr machine list --json`, via `HERDR_BIN_PATH`), addressed by opaque profile ID only; requests omit `machine` (or say `local`, stripped at parsing) for this one. SSH runs on demand for an operation or a watcher restart, never on a retry timer. Remote code must run on the Node a machine has, so avoid recent built-ins there (`Map.groupBy` and the like).
- Time limits flow down from the hooks' `call` timeout as `budgetMs`: nested SSH calls and blocking waits derive theirs from it, and a remote machine gets the time left, not a deadline, since its clock may differ. `$.process.run` allows ten minutes at most (`LONGEST_CALL_MS`).
- `$` reaches only top-level functions of `register.ts` (`bridgeOf`, `sessionIo`, `appendAll`, `runCommand`); imported modules get closures. `tool.call` uses `bridgeOf($)` with its own `$`, because a hook's 10 s budget only pauses while that hook's own `$` calls are in flight.
- A blocking call or an answer being entered leases its worker; the watcher skips leased workers and reconciles them when the last lease ends. Settlement compares the worker's latest input ID with `seenInputId`, so a reply is reported once whichever path sees it.
- Records are keyed by machine and Herdr terminal ID. Pane IDs change on move and Herdr rejects subscriptions naming a missing pane, so the watcher subscribes to each terminal's current pane and reports a move under its previous pane ID.
- Reports raised during a main turn wait in the fleet's outbox and are appended after the next main-loop tool call; what the turn never reached is submitted as the next prompt when it ends. A report raised during a blocking call therefore arrives when that call returns, as in pi-shepherdr. `$.prompt.submit` resolves only when its turn starts: never await it from `turn.complete`. Subagent runs raise `turn.complete` with `agentId` but no `turn.start`.
- After automatic compaction, which resumes mid-turn without `turn.start`, the briefing joins the compacted messages. Between turns (`/compact`, a notes-compaction window) another plugin may replace the conversation after this hook, so it is only marked due and appended at the next turn start. The orchestration guidance rides along when the user chose a mode.
- Current Pi Ask publishes each open question as a `shepherdr-extension-message` entry (text and reply template, no prompts) and takes its answer as an `extension-reply` peer frame, which reaches a blocked worker without a turn; that is the only route to an Ask run inside a Code Mode `exec` cell, whose call never appears as an `ask` tool call. The report carries Ask's own text and reply template as `question`, not prompts. Only Ask's messages are read: `answer` sends Ask's JSON answers, and other extensions' messages have no answer shape in the tool yet. Older Ask's `pi-ask-active` entries and the terminal-driving `pi-ask.mjs` stay for workers that have not updated.
- Background Pi Asks (`delivery: "steer"`) are found by the long-lived watcher, which reads only what each write appended and parses the transcript only when that holds an Ask entry; it scans once at start for Asks opened earlier. They settle through the same `question` path as blocking Asks.
- A remote watcher's stdin stays open for the SSH connection's life and its end stops the watcher, since SSH need not end a remote process without a PTY.
- `bridge/vendor/*.mjs` and `profiles/` started as copies of pi-shepherdr (howaboua-pi-stuff `1f189a2`) and are owned here; nothing goes back upstream. Keep the peer frame compatible with the receiver pi-shepherdr workers run (`PEER_PROTOCOL`, the `message`, `commands` and `extension-reply` kinds).
- `bridge/workers/pi-ask.mjs` drives older Pi Ask's terminal layout (its frame rules, tab row and `Review` step) and must keep refusing to send keys when the frame is not recognized. It returns only after Pi records the Ask's outcome, so a final key that did not take fails the `answer` call, and, for a blocking Ask, after Herdr stops reporting the worker blocked on it (bounded at 15 s; past that the worker is reported as it stands).
- New worker kinds are adapters in `bridge/workers/` exposing `kind`, `program`, `launchArgs`, optional `localOnly`, `sessionPath`, `isReady`, `view`, `deliver`, `commands`, `answer` and `answerStatus`, with questions and answers in the shared shape documented in `workers/index.mjs`; shared code asks the adapter (`workerFor`, `workerOfKind`) rather than testing kinds, and adapters share `envelope.mjs` (the delivered text), `answers.mjs` (answer checks) and the vendor reader's `scanBackward`/`cachedView`. The hooks side knows no kind; it only completes a `session` route (`sendRoute`), the one thing the Node bridge cannot do.
- Claude Code workers take tasks and answers through `$.session.send`, which reaches sessions on this machine only, so `onMachine` rejects any remote result carrying a `session` route and `spawn` refuses Claude profiles on another machine. Herdr's terminal prompt is used only for slash commands: `/quit` types `/exit`, waits for Claude Code to leave the pane, then closes it (the pane would otherwise keep a shell).
- Claude Code holds a peer message for its person when exactly one side bypasses permissions (`bypassPermissions`, or plan where bypass is available); the worker would idle while its controller waits, and `$.session.send` reports nothing. Spawn therefore passes `--settings` with `crossSessionInbound: "accept"`. Only the last `--settings` flag applies, so `profileArgs` folds a profile's own into that one. Attached, non-spawned sessions keep their own setting.
- A Claude worker's open `AskUserQuestion` is answered by its own Shepherdr (`hooks/worker.ts`): the `tool.call` hook races the dialog's `next(e)` against an answer frame keyed by the call's `tool_use_id`. Returning first closes the dialog; the abandoned `next` settles as a rejection the model never reads. `session.receive` consumes every message that is wholly a frame, open or not, so none reaches the model; the controller escapes `<` in the frame's JSON so answer text cannot close it early. `origin.plugin` is only the sender's claim: never guard on it. A worker without this mod loaded cannot be answered this way; `answered` then fails after 10 s.
- Claude Code writes an `AskUserQuestion` call to its transcript only once it settles, so the worker's hook publishes the open question to `$XDG_DATA_HOME/claude-shepherdr/asks/<session id>.json` before calling `next(e)` and writes `{}` after; the bridge reads it uncached beside the transcript, whose recorded result outranks a stale file. A worker without this mod reports a plain `blocked`.
- Claude workers start without `--name` (`launchArgs`): its name bar leaves the question dialog outside the screen region Herdr reads, which then reports the worker idle or done instead of blocked. An attached session started with `--name` still shows that, so `view` reads the published question whatever Herdr's status.
- Claude transcripts (`$CLAUDE_CONFIG_DIR/projects/<cwd, non-alphanumerics as dashes>/<session id>.jsonl`) chain by `uuid`/`parentUuid`; a compaction boundary has no `parentUuid` and continues through `logicalParentUuid`. Inputs are human `user` rows, peer messages (`user`, `isMeta`, `origin.kind: "peer"`), and mid-turn arrivals recorded as `attachment` rows of type `queued_command`; tool results, compact summaries, local command rows and interruptions are not. Spawn passes `--session-id`, so the session is known before its transcript exists; until then `sessionPath` is undefined and settlement runs on Herdr status alone.
- Claude Code trusts exact folders, not their children. A spawn stuck at Pi's or Claude Code's trust prompt reads the pane and says so before rolling back; trusting a folder is the user's decision.
- Claude profiles come from `$XDG_CONFIG_HOME/claude-shepherdr/profiles` when it exists, else `claude-profiles/`; Pi Shepherdr's directory never holds them, since its loader rejects their fields. A name in both sets is refused. `--plugin-dir` shadows an installed copy of the same plugin, which is how a live test gives workers a development build (a temporary Claude profile whose `claude_args` pass it).
- `fs.watch` fails with `EMFILE` and localhost TCP is blocked inside Claude Code's Bash sandbox, so `watch.mjs`, `wait`, `answer` and peer delivery cannot be probed from there; the mod's own processes are not sandboxed.
